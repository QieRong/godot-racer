# 测试与验收

本项目有一整套可自动化的验收检查，全部通过游戏主场景的 `--check=` 通道运行
（原因见文末"为什么不直接用 `--script`"）。

## 怎么跑

```powershell
cd 04-Godot启动器

pwsh -File .\run-all-checks.ps1            # 全部 19 项，最后汇总成一张表
pwsh -File .\run-all-checks.ps1 -Quick     # 跳过 lap/stress/opponents 等耗时项（15 项）
pwsh -File .\run-all-checks.ps1 -Only avoid,pause
pwsh -File .\run-check.ps1 -Check <名称>   # 跑单项
```

启动器菜单里的「4/5/6」是同样的东西。每项的完整日志在 `godot-logs/check-<名称>.log`。

`-Level` 是**0 起**（不传就用默认关卡）；`-NoAi` 用于做"只差对手"的物理 A/B。

### 两道"文档不许漂移"的闸门（套件的第 0/1 项，不启动 Godot）

文档过时是**渐进的、无声的** —— 加了检查项、改了用例条数，没人改文档，
过一阵就出现"文档写的东西早没了""新功能一个字没提"。人眼 review 靠不住
（实测我自己就漏过两回），所以做成机器校验：

| 脚本 | 管什么 | 实测抓到过什么 |
|---|---|---|
| `check-readme.ps1` | **文档 ↔ 项目**：文档提到的路径必须存在；文档提到的 `--check=<名>` 必须已实现；**实现的每个检查项文档必须提到**；文档说的"全部 N 项 / N 个关卡"必须等于实际值 | 新增 `--check=reverse` 后 README 一个字没提 → 红 |
| `check-docs.ps1` | **文档 ↔ 文档与常量**：逐项清单的条数必须等于实现里的计数常量（`LAYOUT_ELEV_CASES` 等）；"全部 N 项 / Quick N 项"必须等于 `run-all-checks.ps1` 的实际项数；Quick 集里的项必须都已实现 | ①文档少算 `reverse` 1 条 ②往 Quick 集加 `reverse` 后文档"13 项"立刻过期 ③`testing.md` 长期停在"53 条" |

⚠ 两者分工不同、都要跑：`check-readme` 看不出"文档自己内部的两个数字打架"，
`check-docs` 看不出"文档提了一个不存在的文件"。套件里两项都在（`docs` 与 `readme`）。

### 2026-09-23 真实碰撞体取证（**推翻了上一条的「几何间隙不足」**）

上一版结论是用 2D 的 `lateral` 标量 + 视觉盒旋转角点（0.95×√2≈1.34）**估**出来的，
两处都不成立，已作废：

- `_place_static()` 里 `mesh.rotation.y = rng.randf_range(0, TAU)` 只加在 **MeshInstance3D** 上，
  同位置的 `CollisionShape3D` **没有任何旋转**（`cs.rotation` 从未被设置）——
  所以碰撞体就是 1.9×1.6×1.9 的**轴对齐**盒，不存在 1.34m 角点；
- 标量 `lateral` 之差也代替不了三维关系（3.4m 长的车体斜着停在 1.9m 石头旁边）。

改用**物理世界里的真实碰撞形状**测量（`ai_opponent._probe_collision_geometry()`，
只在卡住自救时打印一次，不参与任何通过/失败判定）：

**已证明的事实**：

   手工按 AABB 算最小间距也是正的：对石头#1 纵向分离 **+0.41 m**、横向 **+0.15 m**）；
2. 四轮**全部接地**、轮心高度分别 0.315/0.316（前，半径 0.34）与 0.473/0.475（后，半径 0.50），
   与「半径 − 0.025 悬挂压缩」完全吻合 → **正常贴地行驶姿态**，不是骑在石头上、不是翻车；
   车身与中心线夹角只有约 8°；下方向 0.14 m 处就是 Ground；
3. 动态路障此刻在世界另一侧（纵向 +347 m / +237 m），**与卡死无关**；
4. 车速 0.1 km/h；`_update_drive` 那一帧给的是 `engine_force = 0.0`
   —— ⚠ 这只说明「**打印那一刻**控制侧没有给油」（诊断时刻的读数）；
5. `probe_ahead_m()` 在**诊断时刻**读到 **3.36 m** → 按公式限速会被压到 `(3.36−2)²×1.8 ≈ 3.3 km/h`。

**已证明**：

- 车体碰撞盒与 6 块静态石头**逐块不相交**；四轮全接地、轮心高度与「半径 − 0.025 悬挂压缩」吻合
  → 这是**正常贴地行驶姿态**，不是骑在石头上、不是翻车；
- 动态路障此刻在赛道另一侧（纵向 +347 m / +237 m）→ 与这一处停顿无关；
- 横向标量推出的「几何间隙不足」**不成立**（对石头#1 的最小分离为正）；
- 诊断时刻 `probe_ahead_m()` 返回有限值 3.36 m，**这一帧的目标速度确实会被压到约 3 km/h**。

**待确认（不许当结论）**：

- ⚠ **`engine_force = 0` 不能证明「车静止是因为没有给油」**。`_physics_process()` 的顺序是
  `_update_progress() → _update_stuck_rescue() → _effective_lane() → _update_steering() → _update_drive()`，
  而这条诊断是在 `_update_stuck_rescue()` 里打印的 —— **本帧的 `_update_drive()` 还没执行**，
  所以读到的 `engine_force` 是**上一帧遗留值/未更新值**，只能算「诊断时刻的读数」，
  不能当停车因果。要判断控制侧有没有给油，必须另取一份带帧内时序的证据。
- **3.36 m 处那个实体是谁，尚未确认**。`cast_motion()` 在 Godot 4.4 里返回的是
  `[safe_fraction, unsafe_fraction]`（无碰撞 = `[1.0, 1.0]`），
  **不返回命中的 collider**；「盒心细射线没有命中」只能说明「撞的不是盒心正前方」，
  不能推出「撞的是护栏」。本条目在下面的 A/B 取证完成前保持**未确认**。
- 五处自救点里只有第一处做过完整探针，其余四处只打了六个方向的距离；
- 「车为什么会偏到横向 2.51（目标 2.40）」还没有单独取证。
- **probe 是否就是本关卡死的主因，尚未由 A/B 证明**（见下一节）。

**下一步（按这个顺序）**：

1. 先查 `probe_ahead_m()` 的探测盒几何：它必须只对「车体沿当前车头方向真正会扫过的区域」报警，
   而不是把路缘/侧前方的实体也算成「正前方有障碍」；
2. 再决定要不要动关卡几何 —— 目前的证据**不支持**先改石头位置或尺寸。

#### 实验 2：世界轴对齐盒会不会误报

两个疑点分开回答：

1. **会不会把侧前方护栏误判成正前方障碍** —— **不会**。上面五次里，probe 报有限值时

   同一位置、同一 motion，只换盒朝向（车头朝向 vs 世界轴）：

   ```text
   #1  世界轴 0.186（3.35m）  vs  车头朝向 0.045（0.80m）   轴对齐多探 2.55m
   #2  世界轴 0.079（1.42m）  vs  车头朝向 0.048（0.86m）   多探 0.56m
   #3  世界轴 0.059（1.06m）  vs  车头朝向 0.053（0.96m）   多探 0.10m
   #4  世界轴 0.038（0.68m）  vs  车头朝向 0.038（0.68m）   ——
   #5  世界轴 0.081（1.45m）  vs  车头朝向 0.041（0.73m）   多探 0.72m
   ```

   但在**盒角最大横向偏移**上两者都 ≤ 车体半宽 0.875 m

#### B 组窗口读数：车是被"楔住"的，不是被探头刹停的

自救前 400 帧窗口（每 20 帧采样）里 B 组的读数（probe **不参与限速**，所以目标速度是自由值）：

```text
B #2  自救前 3.33s 速度 118.8 km/h  目标速度 157.6 km/h  engine_force -1955.6  brake  1.2
      自救前 2.99s 速度   2.9 km/h  目标速度 156.9 km/h  engine_force -4000.0  brake  1.2
      自救前 0.16s 速度   0.1 km/h  目标速度 156.9 km/h  engine_force -4000.0  brake  1.2
```

`engine_force = -4000.0`（负 = 本项目的前进方向，见 `_update_drive` 的符号约定）是**满油**，
目标速度 156.9 km/h，而车速 0.1 km/h —— **在满油下 3 秒没动**。
A 组在同一位置的读数是"目标速度被 probe 压到 0、engine_force 0"。

→ 所以卡死的本质是**车被楔在石头/护栏之间**；probe 的限速只是**症状**：
它把目标速度压到 0，于是 `_update_drive` 不再给油，看起来像"控制侧踩死了刹车"。
把 probe 摘掉，车确实满油了，但它**依然出不来**（力不够，或已经卡在几何死角里）。

#### 新发现（本轮不修，留给下一轮）：车是"横向漂进"石头里的

五处卡死点里，`intersect_shape` 与两条角点射线给出的相对关系高度一致：
石头在车的**左前方 1.0–1.7 m 横向、1.2–1.5 m 纵向** —— 也就是**车头斜着撞进石头**，
不是"石头正好横在路中间"。

而同一时刻 AI 自己认为的车道是 `+2.40 m`（`_lane_now`），实际横向却已经在
石头那一侧（卡死点 #2：车体世界中心与石头中心的赛道横向差约 **-4.1 m**）。
也就是说：**AI 的"目标车道"没变，变的是车的实际横向位置**，而
`pick_clear_lane()` 判定石头"与车道 +2.40 的横向差 -2.35 > 占用阈值 2.17 → 通行"——
这个判定是基于**理想车道**，而车已经不在那条车道上了。

这条线索指向"横向跟踪/走线"而不是 probe 几何，**属于本轮明令不动的范围**
（`lane_offset` / `racing_line.gd` / 避障算法），所以只记录、不修改。

#### 关于 `cast_motion()` 的口径（避免再次误用）

Godot 4.4 的 `PhysicsDirectSpaceState3D.cast_motion()` 返回
`[safe_fraction, unsafe_fraction]`，无碰撞时是 `[1.0, 1.0]`。
它**不返回命中的 collider**。本文件里出现的"命中=AirWall / 静态障碍"全部来自
**另做的** `intersect_shape` / `intersect_ray`，不是 `cast_motion` 的返回值。

## `run-check.ps1` 的两道闸门

都是踩坑之后加的：

1. **启动 Godot 之前**跑 `lint-gdscript.ps1`（中文串里的 ASCII 直引号、`.bat` 的 CRLF）
   与 **`parse-check.ps1`**（真·跑 Godot 解析器，能抓"类型推断"这类错误）。
   `main.gd` 一旦解析失败，症状是"赛道不生成、车一直往下掉、每个关卡都这样"——
   看起来像游戏坏了，其实是一行代码写错。`parse-check` 的用法：

   ```powershell
   pwsh -File .\parse-check.ps1              # 检查入口脚本（main.gd / menu.gd）
   pwsh -File .\parse-check.ps1 -Scripts res://scenes/main.gd
   ```

   > 为什么不用 lint 一把梭：`lint-gdscript.ps1` 是逐字符扫源码，只能发现引号类问题；
   > **类型推断错误**（对未标注类型的 `Node` 取属性、用 `:=` 接收 `Variant`）
   > 只有让 Godot 自己解析才知道。而这类错误在本项目已经犯过三次。
   > `parse-check` 会过滤 `--check-only` 的已知假阳性（autoload 在那种模式下未注册）。

2. **跑完后**扫日志里的 `Parse Error` / `Failed to load script` 并显式失败。
   因为 `main.gd` 挂掉时日志里**照样有大量正常的 `[自检]` 输出**（来自其它脚本），
   只看那些会以为一切正常。

另外每项检查有**自己合理的最短超时**（`lap` 内部允许跑 6 分钟）。
曾经只给 260 秒，它在第 2 圈就被杀掉，日志只剩 1 圈圈速，
于是"上圈 == 最快"被误判成圈速异常——看起来像代码回归，其实是脚本把进程掐了。

## 为什么不直接用 `--script`

- `godot --path <工程> --script xxx.gd` **必崩**（signal 11，连只 print 然后 quit 的
  空脚本都崩）；而 `--script <绝对路径>`（不带 `--path`）是正常的。
  所以崩溃来自 **`--path` 与 `--script` 的组合**。
- `--headless` 在 4.4.1 里不是有效参数，传了会被忽略并**直接去跑主场景**。
- `--script` 方式本身也不稳，而且启动期偶发段错误。

所以验收一律走主场景自检：`godot --path <工程> -- --check=<名称>`
（在 `main.gd` 里实现，写完日志自动退出；外层 `run-check.ps1` 带重试）。

截图不能用 headless（空渲染器，截出来是空图），走 `main.gd --shot` 钩子：

```powershell
pwsh -File .\shoot.ps1 -Level 4 -Frames 430 -Hold 430 -Out ..\screenshots\shot.png
```

### ⚠ 测"车的位置/姿态"时，截图是**必需证据**，不是补充

日志里的坐标是数字，看不出车在不在路面上。下面这几类问题**只有一张图能一眼定案**：

- 掉头后倒着开（`点积=-1.00` 在日志里极不起眼）
- 卡在护栏**内侧**顶住（出界复位要"护栏外 4m"才触发，内侧永远不触发）
- 贴着墙推头、复位落点偏到路肩外

所以判据是：**数字断言 + 一张图，两个都要**。用 `-Drive` 让自动驾驶把车真开起来：

```powershell

```

- 加 `-Drive`：自动驾驶追线（`_drive_track`），能拍到"车在赛道上的实际位置/姿态"
- ⚠ `-Drive` **刻意不做掉头恢复** —— 被自动修好了反而看不见问题
- `-WrongWay -WrongWayMode 1|2`：给「方向反了」提示留图。
  `1` = 车头拧到赛道反方向后前进（**应**出现提示）；`2` = 车头拧反后按 S 倒车（**不应**出现）。
  两张对照图：`..\shots\reverse-warn.png` / `..\shots\reverse-backward.png`
- 截图前会顺带打印「离中心线多少 / 半路宽多少 / 车头与赛道夹角」，
  夹角 >100° 还会显式标 `✘ 车头朝后！`，**图和数一起看才作数**

### ⚠ 用 `--shot-*` 摆位时必须等赛道建好

赛道是**延迟构建**的（Track 由 `main.gd` 在 ready 后 `build_world.call_deferred()`），

## 方向反向提示（`--check=reverse`）

赛道**只允许顺时针**行驶。玩家撞墙后车头被弹反时要提示他调头；
**允许倒车 —— 倒车不视为"开反了"**（撞墙掉头后按 S 退出来是**正确**的救车动作）。

判定：**车头朝向**与赛道切线做点积，`dot < −cos(enter_deg)` 且速度达标 → 提示。
用**车头**而不是行进方向，正是为了不把"倒车救车"误报成"开反了"。

| 参数（`LevelConfig`，**不得硬编码**） | 默认值 | 说明 |
|---|---|---|
| `reverse_speed_threshold_kmh` | 15.0 | 低于此速度不提示（停车掉头是合法的） |
| `reverse_angle_enter_deg` | 120.0 | 进入提示的角度阈值（`dot < −0.5`） |
| `reverse_angle_exit_deg` | 105.0 | 退出提示的角度阈值（`dot > −0.2588`）；**必须 < 进入值** |

6 条用例（纯函数，逐条对应规格表）：

| # | 场景 | 期望 |
|---|---|---|
| ① | 正向 0°，60 km/h | 不显示 |
| ② | 反向 180°，60 km/h | 显示 |
| ③ | 反向 180°，仅 5 km/h（< 15） | 不显示 |
| ④ | 130°（越过进入阈值 120°），60 km/h | 显示 |
| ⑤ | 130° → 110°（迟滞死区内） | **仍显示** |
| ⑥ | 130° → 90°（越过退出阈值 105°） | 隐藏 |

外加**端到端**（真车 + 真物理 + 真 HUD）：①车头 180° 全油门前进 → 提示必须亮
②按 S 倒车 → 提示必须**一帧都不亮**。

> **注意**：这台机器上 Godot 4.4.1 **启动期**偶发 signal 11（空场景也会），
> 与项目代码无关。所有脚本都内置重试；如果手动跑命令，失败一次请重试。
