# 测试与验收

本项目有一整套可自动化的验收检查，全部通过游戏主场景的 `--check=` 通道运行
（原因见文末"为什么不直接用 `--script`"）。

## 怎么跑

```powershell
cd 04-Godot启动器

pwsh -File .\run-all-checks.ps1            # 全部 18 项，最后汇总成一张表
pwsh -File .\run-all-checks.ps1 -Quick     # 跳过 lap/stress/opponents 等耗时项（15 项）
pwsh -File .\run-all-checks.ps1 -Only avoid,pause
pwsh -File .\run-check.ps1 -Check <名称>   # 跑单项
```

启动器菜单里的「4/5/6」是同样的东西。每项的完整日志在 `godot-logs/check-<名称>.log`。

`-Level` 是**0 起**（不传就用默认关卡）；`-NoAi` 用于做"只差对手"的物理 A/B。

### 两道"文档不许漂移"的闸门（套件的第 0/1 项，不启动 Godot）

文档过时是**渐进的、无声的** —— 加了检查项、改了用例条数，没人改文档，
过一阵就出现"文档写的东西早没了""新功能一个字没提"。人眼 review 靠不住
（实测我自己就漏过两回），所以做成机器校验：

| 脚本 | 管什么 | 实测抓到过什么 |
|---|---|---|
| `check-readme.ps1` | **文档 ↔ 项目**：文档提到的路径必须存在；文档提到的 `--check=<名>` 必须已实现；**实现的每个检查项文档必须提到**；文档说的"全部 N 项 / N 个关卡"必须等于实际值 | 新增 `--check=reverse` 后 README 一个字没提 → 红 |
| `check-docs.ps1` | **文档 ↔ 文档与常量**：逐项清单的条数必须等于实现里的计数常量（`LAYOUT_ELEV_CASES` 等）；"全部 N 项 / Quick N 项"必须等于 `run-all-checks.ps1` 的实际项数；Quick 集里的项必须都已实现 | ①文档少算 `reverse` 1 条 ②往 Quick 集加 `reverse` 后文档"13 项"立刻过期 ③`testing.md` 长期停在"53 条" |

⚠ 两者分工不同、都要跑：`check-readme` 看不出"文档自己内部的两个数字打架"，
`check-docs` 看不出"文档提了一个不存在的文件"。套件里两项都在（`docs` 与 `readme`）。

## 已知缺陷（有实测证据，尚未修）

**AI 在关卡 4（荒漠）会被静态障碍卡死**（2026-09 试玩期间交叉验出来的，属既有缺陷，
不是那次改动引入的；自动化的 `opponents` 一直跑关卡 5，所以此前没暴露）：

- 实测日志：`--check=opponents -Level 3`，AI 连续自救 **9 次**后被超时掐断，位置固定为
  `(-271.27, 1.447, 116.81)`、离中心线 **0.02 m**、姿态 up.y=0.99（没翻）、**接地 2/4**、速度 **0**。
  y=1.45m 远高于正常行驶高度 0.53m → 车是**骑在石头顶上**。
- 机理（推导 + 日志一致）：关卡 4 的**动态滑动路障**扫掠范围约 1.2~4.4 m，**会扫过 AI 的
  2.4 m 巡航车道** → AI 按 `clear_lane_for()` 往中线闪避 → 而静态石头按 `_pick_lateral()`
  就摆在离中线 ≤0.125 m 的带子里 → AI 撞上/骑上石头 → 自救把它推到石头上 → 永远卡住。
- 未采用的修法（改过、验证**没修好**，已回退，不留没证据的改动）：
  让 `clear_lane_for()` 只对动态路障换道。实测仍卡在同一位置 —— 因为触发换道的确实是动态
  路障，问题在于**选替代车道时没有把静态石头算进去**。
- 正确的修法方向（并入赛道重设计阶段 2 的 AI 工作）：
  ① 选替代车道时把**所有**障碍都算作占用；② 找不到空车道时应当**减速排队**而不是硬挤；
  ③ 动态路障的扫掠范围不该覆盖 AI 的巡航车道（关卡设计层面也能改）。

## `run-check.ps1` 的两道闸门

都是踩坑之后加的：

1. **启动 Godot 之前**跑 `lint-gdscript.ps1`（中文串里的 ASCII 直引号、`.bat` 的 CRLF）
   与 **`parse-check.ps1`**（真·跑 Godot 解析器，能抓"类型推断"这类错误）。
   `main.gd` 一旦解析失败，症状是"赛道不生成、车一直往下掉、每个关卡都这样"——
   看起来像游戏坏了，其实是一行代码写错。`parse-check` 的用法：

   ```powershell
   pwsh -File .\parse-check.ps1              # 检查入口脚本（main.gd / menu.gd）
   pwsh -File .\parse-check.ps1 -Scripts res://scenes/main.gd
   ```

   > 为什么不用 lint 一把梭：`lint-gdscript.ps1` 是逐字符扫源码，只能发现引号类问题；
   > **类型推断错误**（对未标注类型的 `Node` 取属性、用 `:=` 接收 `Variant`）
   > 只有让 Godot 自己解析才知道。而这类错误在本项目已经犯过三次。
   > `parse-check` 会过滤 `--check-only` 的已知假阳性（autoload 在那种模式下未注册）。

2. **跑完后**扫日志里的 `Parse Error` / `Failed to load script` 并显式失败。
   因为 `main.gd` 挂掉时日志里**照样有大量正常的 `[自检]` 输出**（来自其它脚本），
   只看那些会以为一切正常。

另外每项检查有**自己合理的最短超时**（`lap` 内部允许跑 6 分钟）。
曾经只给 260 秒，它在第 2 圈就被杀掉，日志只剩 1 圈圈速，
于是"上圈 == 最快"被误判成圈速异常——看起来像代码回归，其实是脚本把进程掐了。

## 为什么不直接用 `--script`

- `godot --path <工程> --script xxx.gd` **必崩**（signal 11，连只 print 然后 quit 的
  空脚本都崩）；而 `--script <绝对路径>`（不带 `--path`）是正常的。
  所以崩溃来自 **`--path` 与 `--script` 的组合**。
- `--headless` 在 4.4.1 里不是有效参数，传了会被忽略并**直接去跑主场景**。
- `--script` 方式本身也不稳，而且启动期偶发段错误。

所以验收一律走主场景自检：`godot --path <工程> -- --check=<名称>`
（在 `main.gd` 里实现，写完日志自动退出；外层 `run-check.ps1` 带重试）。

截图不能用 headless（空渲染器，截出来是空图），走 `main.gd --shot` 钩子：

```powershell
pwsh -File .\shoot.ps1 -Level 4 -Frames 430 -Hold 430 -Out ..\screenshots\shot.png
```

### ⚠ 测"车的位置/姿态"时，截图是**必需证据**，不是补充

日志里的坐标是数字，看不出车在不在路面上。下面这几类问题**只有一张图能一眼定案**：

- 掉头后倒着开（`点积=-1.00` 在日志里极不起眼）
- 卡在护栏**内侧**顶住（出界复位要"护栏外 4m"才触发，内侧永远不触发）
- 贴着墙推头、复位落点偏到路肩外

所以判据是：**数字断言 + 一张图，两个都要**。用 `-Drive` 让自动驾驶把车真开起来：

```powershell
pwsh -File .\shoot.ps1 -Level 0 -Drive -Frames 400 -Out ..\shots\drive-l1.png
```

- 不加 `-Drive`：只能"停着"（`-Hold 0`）或"按住 W 直冲"（`-Hold N`），**开不出正常行驶状态**
- 加 `-Drive`：自动驾驶追线（`_drive_track`），能拍到"车在赛道上的实际位置/姿态"
- ⚠ `-Drive` **刻意不做掉头恢复** —— 被自动修好了反而看不见问题
- `-WrongWay -WrongWayMode 1|2`：给「方向反了」提示留图。
  `1` = 车头拧到赛道反方向后前进（**应**出现提示）；`2` = 车头拧反后按 S 倒车（**不应**出现）。
  两张对照图：`..\shots\reverse-warn.png` / `..\shots\reverse-backward.png`
- 截图前会顺带打印「离中心线多少 / 半路宽多少 / 车头与赛道夹角」，
  夹角 >100° 还会显式标 `✘ 车头朝后！`，**图和数一起看才作数**

### ⚠ 用 `--shot-*` 摆位时必须等赛道建好

赛道是**延迟构建**的（Track 由 `main.gd` 在 ready 后 `build_world.call_deferred()`），
而 `--shot` 的 `_process` **第一帧**就开始跑。在赛道建好之前调
`nearest_on_centerline()` 并摆位，车会落在世界里某个荒谬位置然后**坠落** ——
截图出来是"车速三位数、脚下一片空白大地、小地图全黑"，**看起来像 Godot 启动段错误，
其实是摆位太早**（实测白瞎了两张图才定位）。
所以摆位一律走 `await track.await_world_ready()` + 等半秒物理稳定，见 `_shot_wrongway_warp()`。

## 方向反向提示（`--check=reverse`）

赛道**只允许顺时针**行驶。玩家撞墙后车头被弹反时要提示他调头；
**允许倒车 —— 倒车不视为"开反了"**（撞墙掉头后按 S 退出来是**正确**的救车动作）。

判定：**车头朝向**与赛道切线做点积，`dot < −cos(enter_deg)` 且速度达标 → 提示。
用**车头**而不是行进方向，正是为了不把"倒车救车"误报成"开反了"。

| 参数（`LevelConfig`，**不得硬编码**） | 默认值 | 说明 |
|---|---|---|
| `reverse_speed_threshold_kmh` | 15.0 | 低于此速度不提示（停车掉头是合法的） |
| `reverse_angle_enter_deg` | 120.0 | 进入提示的角度阈值（`dot < −0.5`） |
| `reverse_angle_exit_deg` | 105.0 | 退出提示的角度阈值（`dot > −0.2588`）；**必须 < 进入值** |

6 条用例（纯函数，逐条对应规格表）：

| # | 场景 | 期望 |
|---|---|---|
| ① | 正向 0°，60 km/h | 不显示 |
| ② | 反向 180°，60 km/h | 显示 |
| ③ | 反向 180°，仅 5 km/h（< 15） | 不显示 |
| ④ | 130°（越过进入阈值 120°），60 km/h | 显示 |
| ⑤ | 130° → 110°（迟滞死区内） | **仍显示** |
| ⑥ | 130° → 90°（越过退出阈值 105°） | 隐藏 |

外加**端到端**（真车 + 真物理 + 真 HUD）：①车头 180° 全油门前进 → 提示必须亮
②按 S 倒车 → 提示必须**一帧都不亮**。

> **注意**：这台机器上 Godot 4.4.1 **启动期**偶发 signal 11（空场景也会），
> 与项目代码无关。所有脚本都内置重试；如果手动跑命令，失败一次请重试。
