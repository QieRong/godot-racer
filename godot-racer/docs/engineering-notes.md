# 工程笔记：踩过的坑与验证方法

这份文件记录**改代码前必须知道的东西**。都是实际调试得出的结论，不是推测。
命令与检查项的用法见 [testing.md](testing.md)。

## Godot / GDScript

1. **`Transform3D(...)` 前 9 个参数是按行给基向量**，按列填 = 填了转置矩阵。
2. **`VehicleWheel3D.position` 是"悬挂塔顶"不是轮心**，静止时硬点高度 =
   `wheel_radius + wheel_rest_length`。把轮心坐标直接填进去会让悬挂一开始就压到底。
3. **前进用的是负 `engine_force`**（与直觉相反，实测得出）。正力矩会让车倒着走。
4. **场景里给导出节点变量赋值必须在 `[node]` 行写 `node_paths=PackedStringArray("xxx")`**，
   否则是 null。
5. **`CenterOfMassMode.AUTO` 会按碰撞盒算出约 0.55 m 的质心，那个高度会侧翻**。
   必须显式设 `CENTER_OF_MASS_MODE_CUSTOM` + `center_of_mass = (0, 0.20, 0)`。
   ⚠ 注意：**换脚本**（`set_script`）时原脚本的 `_ready` 不会跑，
   所以 AI 车必须自己设质心，否则会成片翻车。
6. **`PROCESS_MODE_WHEN_PAUSED` 同时管输入投递**：这个模式下节点**只在暂停时**接收
   `_input`/`_unhandled_input`。用 `pause_menu.gd` 时如果设成它，
   没暂停时收不到输入 → **ESC 永远触发不了暂停**。要用 `PROCESS_MODE_ALWAYS`。
7. **换脚本的顺序**：`set_script()` 必须在 `add_child()` **之前**，
   否则实例自带脚本的 `_ready` 会先跑完。
8. **`GPUParticles3D` 的粒子外观必须用 `draw_pass_1` 指定**。
   挂一个子 `MeshInstance3D` 是错的——那只会在发射点渲染**一个**静止网格。
   症状很隐蔽：日志一切正常，画面上一个粒子都没有。
9. **`albedo_color` 与 `albedo_texture` 是相乘的**：有贴图时要把 `albedo_color` 归白，
   否则草地绿会把雪地贴图染成暗绿。
10. **拷进工程的 PNG 没有 `.import` 文件时，运行时 `ResourceLoader.exists()` 返回 false**。
    必须跑一次 `godot --path <工程> --import`。`.godot/` 缓存可忽略，但 `*.import` 要入库。
11. **`var x := ...` 的类型推断**：`load()` 返回 Variant；对未标注类型的 `Node`
    取属性再 `.method()` 也是 Variant。用 `:=` 推断会**直接解析失败**，
    进而让整个 `main.gd` 加载不了（现象是赛道不生成、车掉落）。要显式写类型。
12. **`Input.parse_input_event()` 在验收环境里喂不进 `_unhandled_input`**，
    看起来像"按键功能坏了"。要测输入链路请用 `get_viewport().push_input(ev)`。

## 赛道生成

13. **`Curve3D.sample_baked(d)` 的 `d` 不是真实弧长**（这是"起点旁边没封住"的真正根因）。
    实测：`d=1631.11` 与绕回的 `d=1635.12` 参数差 4.01 m，而两点**实际距离 23.63 m**——
    缝附近参数被严重压缩。所以"按 `d = i * step_len` 均匀步进"会在闭合缝处留下真实缺口。
    正确做法：从当前点出发逐渐加大 `d`，直到**实际位移**接近目标段长才落点。
14. **椭圆上弦长 ≠ 弧长**：护栏墙**不能**沿起点切线拉一条直弦，弯道外侧每段会短一截，
    实测每 ~21 m 就漏一个 0.1~0.8 m 的口子。正确做法是在**每个环点**上算墙的位置，
    相邻环点的墙点连线成条带。
15. **护栏必须合并成单个 `StaticBody3D`**，否则几十个物理节点的开销会压垮物理帧。
16. **`Track._ready()` 比 `main.gd._ready()` 先跑**（节点顺序），
    所以在 `main` 里 `set(radius_x)` 之后指望 `Track` 读到是**不可能**的——
    实测五个关卡的曲线长度全是默认值。正确做法：把 config 交给 Track，
    由 `main` 显式 `build_world.call_deferred()`（`build_world` 幂等）。

## 物理与操控

17. **墙面必须给 `physics_material` 低摩擦（0.05）**。默认摩擦 1.0 会让车浅角度切入时
    被"咬住"：前后受力抵消，满油门车速也只有 0.3~3 km/h。实测卡墙验收从 4/12 提升到 12/12。
18. **楔入救援**（给油+低速+贴墙 → 沿墙法线位移 0.8 m）必须保留，低摩擦只是缓解。
19. **出界判定的阈值必须与速度无关**。曾经设成"≥8 m/s 时余量收到 0.3 m"，
    结果贴墙跑到 8.5 m/s 就被判出界 → 复位 → 再贴墙 → 再复位，
    表现就是用户报的"快回到起点时一直在重置"。
    现在基线 = 护栏中心线 + 车身半宽 + 4.0 m 余量（约 13.2 m），并带复位死循环断路器。
20. **计圈用几何压线判定**（把车的位置投影到起终点线的前方轴取有符号距离），
    **不要用 `Area3D` 信号**——实测会漏检/误触发。
21. **出生点/复位瞬间必须抑制压线判定**，否则会被算成跑完一圈（"复位白送一圈"），
    现象是"上圈和最快圈显示成同一个时间、而且本圈不计时"。
22. **贴边降速的判据不能用"离中心线的比例"**：AI 本来就跑在偏移车道上，
    8 m 宽关卡的 `半路宽 × 0.6` 正好等于它的车道偏移，会从第一帧起就一路收油跑不动。
    要用**绝对边缘位置**。
23. **`Performance.TIME_PHYSICS_PROCESS` 的逐帧读数噪声很大**：同一套配置连测 5 次得到
    3.04/3.31/3.81/5.53/6.36 ms，甚至出现"4 台对手比 0 台还便宜"的荒谬结论。
    判断"帧率稳不稳"要用**实际达成的物理步频**（3 轮 × 600 帧）。

## 小地图

24. **不要给小地图单独开 `World3D`**（会拿到 null world 并报
    `Parameter "scenario" is null`）。共用主世界 + `cull_mask` 只留
    `MAP_LAYER (1<<16)`，把地面视觉挪到第 18 层让主视角仍能看到。
25. **相机固定包住全图，不要每帧跟随车辆**——跟随会让读图时没有稳定参照系。
26. **标记尺寸要按相机实际分辨率算**：正交 `size=760` 铺约 200px → 约 3.8 世界单位/像素。
    10 单位的标记只有约 2.6px，校验能过但肉眼看不见。
27. **对手/障碍的颜色会和检查点撞**：检查点是青色实心方块，
    所以对手用**黄绿空心圆环**、障碍用**红空心方块**，颜色+形状双重区分，并加图例。

## 脚本 / 启动器（编码相关，最容易无声出错）

28. **中文串里绝不能出现 ASCII 直引号**（`"...（见上方"x"行）"`）。
    它会把字符串提前截断，导致**整个 .gd 解析失败**。
    同一个坑踩了两次，所以做成了机器检查 `lint-gdscript.ps1`，并接进 `run-check.ps1` 的
    preflight——lint 不过就**不启动 Godot**。
29. **cmd.exe 按控制台代码页解析 `.bat`**，这台机器不保证是 UTF-8。中文内容会被误解析并
    吞掉后面的 ASCII（`echo` 变成 `ho`、`if` 断掉），脚本整个散架。
    所以 `.bat` 内容一律**纯 ASCII**，中文界面放在 PowerShell 里。
30. **用 ASCII 编码写 `.bat` 时，里面的中文文件名会被静默替换成 `?????`**。
    所以脚本引用一律用 ASCII 文件名（`launcher-menu.ps1` / `run-all-checks.ps1` / `run-check.ps1`）；入口 .bat 只保留"A Chinese-named menu entry + 3 个直action"，内容全 ASCII。
31. **`.bat` 必须是 CRLF 换行**，只有 LF 会把多行黏成一条命令，双击就是"窗口一闪而过"。
    `.gitattributes` 的 `eol=crlf` **只管检出时**，脚本直接写文件时不会帮你转。
    已做成 `lint-gdscript.ps1` 的第二类检查。
32. **Windows PowerShell 5.1 按 ANSI/GBK 读 `.ps1`**，没有 BOM 时中文全乱码。
    含中文的 `.ps1` 都要带**单一** UTF-8 BOM。
    ⚠ 别写成双 BOM：读文件时 `UTF8.GetString` 会把 BOM 保留成 `U+FEFF` 字符，
    再写入时又加一个，于是 `\uFEFF#` 不再是注释行，报 `'#' 不会被识别为 cmdlet`。
33. **窗口化运行必须用 `start` 分离启动**；从受限 shell 里前台启动渲染同样会段错误。
34. **别用 `| Select-Object -First N` 截 Godot 的输出**：PowerShell 截断后会提前把 Godot
    杀掉，日志只剩前几行，看起来像"启动失败"，其实是抓日志的方式错了。

## 网络 / OpenRouter

35. **不要拿 `curl` 的结论判断 Godot 能不能联网**：Godot 的 `HTTPRequest` 用自带 mbedTLS，
    **不走 Windows schannel**。实测命令行 `curl` 报 `SEC_E_NO_CREDENTIALS` 时 Godot 照样能通。
36. **超时必须可配置且必须有截止时间**。免费档模型首字延迟 3~15 秒，
    1 秒超时会 100% 假超时。关键是"到点必须放弃"，绝不允许 `await` 永久挂住主循环。
37. **模型名不能靠记忆写死**：跑 `--check=models` 探活实测后再填。
    教训：`meta-llama/llama-3.1-8b-instruct:free` 已下架返回 404，
    一个消失的备用模型等于没有备用。
38. **输出被 `max_tokens` 截断时按大括号配对抢救**完整对象，而不是整批丢弃。
39. **只给 AI 模块挂代理**，不动系统代理、不开 TUN——否则梯子一断，
    DSH 等本地回环服务一起不可用。

## 维护脚本时的 PowerShell 陷阱

40. **数组传给函数会被展平，导致 `$p[0]` 变成"第一个字符"**。
    我把"成对替换"写成 `Fix-Text $file @( @('旧','新') )`，函数里
    `foreach ($p in $pairs) { $t.Replace($p[0], $p[1]) }`，
    结果 `$pairs` 被展平成 `('旧','新')`，于是 `$p` 是**字符串**，
    `$p[0]`/`$p[1]` 取到的是**第一个字符 `.`** 和**第二个字符 `\`** ——
    等价于"把全文所有 `.` 换成 `\`"，把 `$Only.Count` 写成 `$Only\Count`、
    `$_.结果` 写成 `$_\结果`，整个脚本报废。
    **教训**：批量改文件用"定点编辑"或哈希表，别自己写通用替换器；
    真要写就用 `,[array]` 或 `[pscustomobject]` 显式包住，并且改完**必须**
    跑一次语法检查 + 实际运行 + 扫描"变量后跟反斜杠"的痕迹。
    （受害文件已从 git 恢复并重新定点修改。）
41. **别用 ASCII 编码写含中文的脚本文件**：会把中文（包括字符串里引用的
    **中文文件名**）静默替换成 `?????`，调用就失败。

## 翻车 / 腹部贴地（P3）

42. **"四轮全不接地"必须单独一条判据**。翻车判定看 `up·UP`（腹部贴地时 ≈1，判不出），
    "卡住"判定看速度（贴地滑行时 27 km/h，也判不出）—— 结果是这个状态**没有任何判定在管它**，
    日志实测它能以 27 km/h 横向滑行 10 秒以上脱不了困，玩家感受就是"车不听使唤"。
    现在：`接地=0/4` + 姿态水平 + 贴着路面 + 还在动，持续 `belly_slide_grace`（1.5 s）
    → 扶正 + 抬起 + 清零线速度/角速度 + 补向上速度增量。
43. **`apply_central_impulse` 的单位是 N·s，不是速度**。本车约 1000 kg，
    直接给 `Vector3.UP * 0.5` 只产生 0.5 mm/s 的速度增量 —— **等于没给**，
    下一个物理帧车又贴回地面（这正是"扶不起来"的机理）。施加时要乘 `mass`。
44. **验收夹具用 `gravity_scale = 0` 把车"悬"住，不要施加升力**。
    实测施加 `mass * 9.8` 的向上力**托不住**：车在 0.5 s 内就落回地面、轮子重新抓地，
    速度从 24.4 km/h 掉到 1.2 km/h，状态根本没维持住。另外夹具给速度必须
    **沿赛道方向**：第一版给的是侧向速度，车 1 秒内横着撞上护栏，同样维持不住。
    还有一条诚实结论：**用 6 个"真实姿态"（水平/滚转/俯仰 + 27 km/h）都复现不出持续贴地** ——
    逐帧统计下 0/4 最多只维持 0.22~0.33 s（占全程 1~7%），车很快落回四个轮子。
    所以 `--check=flip` 里那 6 个姿态只当**证据收集**，硬断言放在合成夹具上，
    复现不出来就明确写"未能复现"，绝不当成通过。
45. **"帧数 ÷ 60 当秒数"的时间标签会系统性错 2 倍**。本工程
    `physics_ticks_per_second = 120`，而 `physics_monitor.gd` 的 `_frames` 是在
    `_physics_process` 里递增的，`_frames / 60.0` 得到的 t 是**真实时间的 2 倍**。
    按这个 t 去对齐事件会整体错位 —— 排查腹部贴地时我就因此把"落地瞬间"误读成
    "持续贴地"，白追了一轮。写时间标签一律除以 `Engine.physics_ticks_per_second`。

## Curve3D / 赛道几何（2026-09 新增，两条都是实测出来的事实）

46. **Godot 4 的 `Curve3D` 没有 `cubic_interp` 属性**。控制点之间插值方式不是靠这个开关，
    能配的只有 `bake_interval`。写 `c.cubic_interp = true` 会报
    `Invalid assignment of property 'cubic_interp'` → **曲线对象失效** →
    `get_baked_length()` 拿到 null → 曲线长度 0 → 路面/护栏/检查点全都不生成 →
    **车掉进虚空、小地图全黑**（用户实测就是这个现象，还配了截图）。
    现在 `track_generator.build_world()` 里加了一道闸门：曲线长度 < 50m 就 `push_error` 吼出来，
    绝不静默往下走。
47. **`Curve3D` 默认是折线，不是样条**。`add_point()` 的 in/out 手柄默认是零向量，
    此时控制点之间就是直线段 —— 也就是说**现役赛道一直是一条 64 边形**
    （64 个控制点，每 ~25m 一个 5.6~7.7° 的折角，曲率无穷大）。
    当年"直线+圆角矩形接点曲率突变把车弹飞"的根源就在这类折角。
    要做真曲线必须自己给手柄：Catmull-Rom 取 `tangent = (next - prev) / 6`，
    闭合时**先去重末点、再用环形邻居**算首尾手柄，且**收口那个重复点必须给同样手柄**
    （给零手柄会让最后一段退化成直线段，两端各冒一个硬折角，实测曲率跳变 0.87/m）。
48. **曲率必须在"最终 Curve3D"上量，不能在折线上量**。在折线上量到的是多边形折角
    （椭圆上每角 5.6~7.7°），会把好赛道误判成不合格；而且 `sample_baked(total)` 常常
    与上一个采样点**几乎重合**（间距 0.00m），除出来的曲率会爆成 0.87/m ——
    这两种都是"量法造成的假警报"。现在：在曲线上按固定弧长采样、跳过间距 < step/4 的点对。
49. **护栏视觉面必须有厚度，否则车尾会"穿模"**（玩家反馈 + 截图）。
    车的**碰撞盒**是 `1.6×3.4`，**视觉包围盒**是 `1.73×3.74`；车斜着贴墙时视觉角点
    比碰撞角点多探出 `0.065·cosθ + 0.17·sinθ`，**理论最大 0.18m**（θ≈69°）。
    护栏原来只是一张**零厚度的面**且与碰撞面重合，于是这 18cm 会从墙的背面露出来 ——
    相机一旦在墙外侧（追尾视角在窄弯里就会出去），正好看见车尾"扎进墙里"。
    修法：视觉护栏做成**有厚度的墙体**（内侧面 = 碰撞面、外侧面 +0.35m、顶面），
    探进墙里的部分被墙体自己挡住。`--check=wallslide` 现在逐帧量
    「车视觉模型相对中心线的最远横向距离」，并要求它 ≤ 墙面 + 墙厚。
50. **`--check-only` 的"已知假阳性"必须重定向掉，不能刷在用户控制台上**。
    `parse-check.ps1` 用聚合脚本一次解析全部 .gd，而 `--check-only` 不注册 autoload，
    所以 Godot 会打印 `Identifier not found: GameState` 之类 —— 我们**过滤**了它们并判定通过，
    但 Godot 的原始 stdout/stderr 仍直接刷在控制台（玩家实测截图：一堆 SCRIPT ERROR
    紧跟一句"检查通过 ✔"，看起来完全像游戏坏了）。
    修法：`Start-Process` 加 `-RedirectStandardOutput / -RedirectStandardError` 落进
    `godot-logs\parse-*.out.log`，控制台只留我们自己的一句说明。
51. **测试"车的位置/姿态"必须补截图 —— 数字会骗过验收**（2026-09 玩家实测反馈后定的规矩）。
    玩家报"方向相反 + 卡墙"时，`--check=lap` 是**全绿**的（L1 三圈 36.7~40.8s、复位 0），
    因为那项检查只验圈速。而物理日志里其实躺着 5 行 `点积=-1.00 ✘ 车头朝后` +
    后轮 `force=-4000`：车被撞掉头后，自动驾驶无条件按死的 W 变成"全油门朝赛道反方向推"，
    以 18~23 km/h 倒着滑了 7 秒。**坐标数字看不出这件事，一张图一眼就定案。**
    所以：截图能力本身要够用。原来 `--shot` 只能"按住 W 直冲"或"停着打方向"，
    **根本没法给"车在赛道上的实际位置"留一张图** —— 于是新增 `--shot-drive=1`
    （`shoot.ps1 -Drive`），用自动驾驶把车真开起来再截，并在截图前顺带打印
    「离中心线多少 / 车头与赛道夹角」，图和数一起看才作数。
    ⚠ 这条规矩后来立刻兑现了价值：`--shot-drive` 第一次跑就拍到车稳稳在路面内、
    夹角 0.1°、109 km/h（`shots/drive-l1-autopilot.png`）。
52. **恢复/扶正不能用 `nearest_on_centerline()` 返回的 `forward`**。
    车被撞到 180° 掉头之后，"离车最近的中心线点"**在车身后方**，它的 `forward`
    因此指向**反方向** —— 拿它扶正等于"把车头朝赛道反方向摆在路中间"，
    自动驾驶接着沿反方向开、撞对面护栏、再卡住、再扶正（实测 aidiag 结束时仍有 54.8°）。
    正确做法：在**整圈**弧长上找"朝向与车头最匹配"的那一点
    （`_drive_best_track_arc`，2 m 一档粗扫 + `nearest_on_centerline` 收敛）。
    ⚠ 扫描范围**默认必须是整圈**：限死在车辆附近（第一版 ±120m）会在错误的一段里
    挑一个相对最好的，越修越偏。这个坑白耗了两轮 90 秒回归才定位。
53. **"快失败"的分支要走进去，就必须能看见它为什么没走进去**。
    `_drive_recover` 里的"直接扶正"分支因为车速门限（3 km/h）没被触发，
    日志里**只有**"倒车+满舵"那一行，完全看不出是哪道门挡住的 —— 又白跑一轮回归。
    现在扶正分支会打印 `[门限自查] 夹角=… 车速=… 扶正上限=…`，找不到匹配点也会明说。
    凡是"条件不满足就静默走另一条路"的地方，都该把这句自查打上。
54. **⚠「反推」是不可靠的：所有诊断一律用正向打印。**
    这是本工程最贵的一条教训（任务 15「AI 速度太慢」把因果搞反过一次）。
    当时 `_target_speed()` 里 `frac` 被 `clampf(..., min_speed_frac, 1.0)` 截断过，
    我从"最终目标 43.2"**反推**弯度，得 101°，于是判断"公式把弯读大了"；
    实际上 43.2 是**下限饱和**的结果（`144 × 0.30`），反推出来的只是**下界**，
    根本不能用来判断公式对不对。**饱和一旦发生，反推就丢掉了真值。**
    现在 `ai_opponent.gd` 有 `debug_bend_at(arc)` / `_debug_bend_detail(arc)`
    （与生产代码**同一个纯函数** `racing_line.bend_angle_deg()`，不做 clamp、不取 min），
    `--check=aidiag` 直接正向打印 `策略=… (裸弯 …°@d=…) 物理上限=… 最终目标=…` 四列。
    规矩：**要看哪个量，就把那个量直接打出来；不要从别的量倒推。**
55. **诊断要打"能区分两种假设"的量，而不是打一个汇总量。**
    「AI 为什么慢」这个现象同时支持两个假设：①公式把弯读大了；②`min_speed_frac` 把它钳住了。
    只打一个"最终目标 43.2"**两个假设都成立**，根本没法区分（我因此白追一轮）。
    `_debug_bend_detail()` 把每一档的 `段长 / 旧口径 |a| / 夹角` 全摊开，差别一目了然：
    实测第一档 `|a| = 0.5~0.6m`、夹角 `101.5°~121.1°` ——
    **同一段直线上读数能漂 20°**，这就直接证伪了"弯度"这个解释（几何量不会这么漂）。
    设计日志时问自己：**哪个数字能证伪其中一个假设？** 打那个。
56. **退化向量：过短的参考向量求夹角在数值上没有意义，必须设下限守卫。**
    AI 一直跑在自己的车道点上，所以"车位置 → 第一个车道采样点"这段向量只有 **0.5~0.6m**；
    拿它和 12m 的线段求夹角，实测得到 **101°~121°**（R≈200~500m 的直线上几何不可能）。
    旧守卫是 `> 0.5m`，刚好放行；于是这个**纯噪声**被当成"最严格的一档"，
    把策略限速压到 `clampf(1 − 101/25, 0.30, 1.0) = 0.30` → `144 × 0.30 = 43.2 km/h`。
    修法：`racing_line.MIN_BEND_SEG = 3.0`，**两段都要够长**才求夹角，任一段退化就整对跳过；
    并且改用量"点列内相邻两段"的夹角（`bend_angle_deg(points)`），从根上不产生退化向量。
    ⚠ **`min(43.2, 146) = 43.2`** —— 不修这条，物理上限在 L1 上永远没有发言机会。
    所以"接物理上限"这个任务里，退化向量修复**不是可选项**（因果依赖，不是两个变量）。
57. **判据要用"能区分改前改后的量"，别用不区分的量。**
    任务 15 里我原本设计"最终目标 ≥ **物理上限** × 85% 的帧占比 ≥ 80%"，
    实测发现它**改前改后都是 0%**：L1 上是**策略**在限速（目标 94~130），
    地面能给到 138~276 —— "离物理上限还有一半"是**正常且安全**的。
    换成"≥ **本关极速** × 85%"立刻能区分：改前 0%（被钉在 43.2/144=30%）、
    改后 1515/2375（63.8%）。
    ⚠ 同一类错误还有一个更隐蔽的版本：**用最大值当判据**。
    我一度用"最终目标最大值 ≥ 80"当哨兵，结果**改前实测最大值就是 117.7~118.0**
    （噪声折角偶尔自己就小了），哨兵判据在坏状态下照样绿。
    现在改成"被钉住的帧占比"（改前 72.3% ✘ / 改后 0.0% ✔）。
    **凡是靠单点/极值当判据的，都要问一句：坏状态下它会不会碰巧过？**
58. **`--check-only` 报 `Could not preload res://scenes/main.gd` 时，真实行号在 `--verbose` 里。**
    `parse-check.ps1` 用聚合脚本一次解析全部 .gd，Godot 对这种失败**只报一行**
    "Could not preload resource script" + "Could not resolve script"，
    **不说错在哪个文件哪一行**（我真因此摸黑找了半小时）。
    加法：`Godot --verbose --check-only --script res://scenes/main.gd`，
    它会打出 `Parse Error: ... at ... (res://scenes/main.gd:1793)`。
    ⚠ 那次的实际错误是"一次编辑吃掉了换行"，把 `var resc := …` 和紧跟的 `print(…)`
    **粘成了一行** —— 症状正是玩家截图里的 **353 km/h、赛道不生成、小地图全黑**。
    这里也再次印证 AGENTS.md 那条规矩：**改完必跑 `parse-check` 再跑验收**，
    否则"脚本没加载"会被当成"物理坏了"。
59. **⚠ 编辑代码时"吃掉换行"会把两条语句粘成一行 —— 现在有机器闸门了。**
    这是第 58 条那次事故的**根因**，也是它最贵的地方：症状（353km/h 空场景）与原因
    （少一个换行）之间隔着一次整个脚本的解析失败，肉眼在 diff 里几乎看不见。
    修法（两道闸门，都在 `04-Godot启动器`）：
    - `lint-gdscript.ps1` 新增第三类检查「两行粘成一行」，判据（**刻意保守**）：
        A. **行中间**出现 TAB —— GDScript 缩进只在行首，行中 TAB 必是两段粘住；
           但要排除两种合法写法：**TAB 对齐行尾注释**（`hud.gd:129` 就是）、
           以及 TAB 落在注释正文里。第一版没排除，一口气误报了几十条。
        B. 一行里出现 ≥2 个 `var`，或 `var` 声明之后又跟 `print/return/for/while/func`。
           关键词表里**故意没有 `if`** —— 行内三元 `var x := 1.0 if c else 0.0` 是合法写法。
    - `parse-check.ps1` 失败时新增**自动逐文件定位**：聚合一红就逐个文件
      `--check-only --script <该文件>` 单独解析，直接打出「真凶文件 + 行号」。
      ⚠ 关键实现细节：**必须直接检查该文件**，不能再 `preload` 包一层 ——
      包一层时 Godot 只报 `Could not preload ...`，**连 `--verbose` 都不给行号**（实测）。
    实测：把当年那一行原样注入 `main.gd`，lint **秒级**报出 `main.gd:1810`；
    删掉 lint 这层、只靠 parse-check，也能在约 20 秒内自动定位到同一个行号。
    （改造前：手动逐个 preload 试了半小时。）
60. **判断"改前改后"的判据，必须先验证它**在两边的读数确实不同。
    任务 15 里我设计了三条判据，其中**两条一开始是坏的**，都是靠"拿改前状态实测一遍"
    才发现的：
    - 「最终目标 ≥ **物理上限** × 85% 的占比」：改前 **0%**、改后 **0%** —— 不区分状态。
      因为 L1 上是**策略**在限速（130），地面能给 275，"离上限还差一半"是正常的。
    - 「最终目标最大值 ≥ 80」：改前实测最大值就是 **117.7~118.0** —— 哨兵在坏状态下**假绿**。
      原因是噪声折角会漂，少数帧自己就小了。
    结论：**判据写完必须拿"已知坏状态"跑一遍**，确认它真红；
    否则你得到的是一条永远绿的假判据（比没有判据更危险，因为它给人安全感）。
    真正稳健的是**占比/分布类**判据（被钉住的帧 72.3% → 0.0%），不是极值类。
61. **低抓地力关卡要单独判，不能拿"极速"当唯一标尺。**
    同一个限制在两类关卡上来源不同：L1 抓地力富余 → 限制来自**策略**；
    L5 冰面（a_lat=8.0）→ 限制来自**地面**。所以"跑不到极速 85%"在冰面上是**正确**行为
    （地面只给 50~158，极速 216）。只卡"≥ 极速 × 85%"会把正确行为判成失败。
    现在 `--check=aidiag` 的第 ③ 条**两条口径都算、取较大者**：
    策略侧 ≥ 极速×85%（L1 实测 61.5%）/ 地面侧 ≥ 物理上限×85%（L5 冰面实测 85.2%）。
    而"AI 太慢"这个 bug 会让**两条都低**（改前 L1：0% / 0%），所以取 max 仍然拦得住。
